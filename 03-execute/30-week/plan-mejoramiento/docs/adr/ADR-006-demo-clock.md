# ADR-006: vencidos reproducibles mediante API

- Estado: propuesta; debe validarse en T-21 antes de considerarla resuelta.
- Contexto: T-21 exige tres líneas vencidas; el cliente no puede enviar `loaned_at` y los préstamos nuevos vencen dentro de cinco días. Sembrar por SQL o agregar un endpoint de fechas rompería requisitos.
- Decisión: puerto `Clock` con reloj real por defecto. Solo una instancia aislada en `APP_ENV=testing` y con configuración explícita podrá leer un archivo temporal de reloj bajo un volumen local ignorado. El perfil normal y producción rechazan esa configuración. El sembrador sigue usando exclusivamente las 21 operaciones HTTP para modificar datos del negocio.
- Procedimiento previsto: arrancar instancia de demostración sin operadores reales; fijar reloj a seis días antes; crear por API exactamente tres préstamos de una línea para tres investigadores distintos; devolver el reloj al presente y autenticar de nuevo porque el JWT anterior expiró; crear los restantes préstamos y devoluciones hasta sumar >=40 equipos, >=10 investigadores y >=15 préstamos, conservando exactamente tres líneas vencidas. Restaurar reloj en `finally` incluso ante errores y comprobar la restauración. No reiniciar ni borrar datos personales o históricos ajenos.
- Alternativas: esperar cinco días (no reproducible en la revisión); SQL directo (prohibido para el sembrador); aceptar fechas por HTTP (amplía el contrato); reloj modificable en producción (altera decisiones del negocio).
- Consecuencias: las pruebas de concurrencia no se ejecutan mientras cambia el reloj. La carga de 5.000 equipos será un modo separado de demostración por API. El mecanismo de reloj no cambia las fechas de Git ni la evidencia de trabajo.
- Evidencia requerida: tres vencidos por endpoint, reporte con filas, cantidades por API, restauración después de un fallo inducido y rechazo de configuración de reloj en entorno normal/producción. Si el mecanismo no pasa esos controles, T-21 sigue pendiente.
